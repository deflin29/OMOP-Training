Why everyone converts to OMOP

A study is written once and sent to every data partner. Each partner runs the same code on its own OMOP copy and returns only aggregate results. This works because every database has the same tables and the same concept IDs, which is what steps 1 and 2 buy you.

Day 3: what PatientProfiles measures

Every PatientProfiles function looks at one person around one date, the index date, and writes the answer into a new column. This is one person from my_cohort.

# the R that produces those columns (your Day 3 script)
cdm$my_cohort |>
  addDemographics() |>                                   # age, sex, prior/future observation
  addCohortIntersectFlag(targetCohortTable = "medications",
                         window = c(-365, -1),
                         nameStyle = "prior_{cohort_name}") |>  # prior_heparin
  addTableIntersectCount(tableName = "condition_occurrence",
                         window = c(-365, -1),
                         nameStyle = "prior_conditions")       # prior_conditions

Glossary

The terms the slides assume you know, in plain words.

CPRD Clinical Practice Research Datalink
Anonymised UK GP records for millions of patients. CPRD GOLD uses Read codes and CPRD Aurum uses SNOMED-based codes. Researchers often use it converted to OMOP. The course uses synthetic data instead.
OMOP Observational Medical Outcomes Partnership
The project that created the data model and vocabularies. The OHDSI open-science community maintains them today.
CDM Common Data Model
The fixed set of tables and columns every OMOP database has: person, observation_period, condition_occurrence, drug_exposure, measurement, death, plus the vocabulary tables.
ETL extract, transform, load
The one-off job that converts a source database into the CDM and maps its local codes to standard concepts. Data partners do this. You don’t, in this course.
Concept ID
The number OMOP gives each clinical idea: 80180 is osteoarthritis, 1367571 is heparin. Names and hierarchy live in concept, concept_relationship and concept_ancestor.
Standard vocabularies
SNOMED CT for conditions, RxNorm for drugs, LOINC for lab tests. Local codes such as Read or ICD-10 are mapped onto these during ETL.
Codelist
A named list of concept IDs that together identify one thing, such as list(arthritis = c(80180, 80809)).
Cohort
The people who meet a definition, with the date each one enters and leaves. Always four columns: cohort_definition_id, subject_id, cohort_start_date, cohort_end_date.
Phenotype, phenotyping
A phenotype is the rule set (codelists plus logic) that finds people with a condition in the data. Phenotyping is building that rule set and checking it finds the right people. That is Day 2, with PhenotypeR for the checks.
Observation period
The time a person is visible in the database, for example while registered with a GP. Outside it, a missing record tells you nothing.
Index date
The date characteristics are measured against. For a cohort it defaults to cohort_start_date.
Window
A time range in days relative to the index date. c(-365, -1) is the year before, excluding the index day. c(0, Inf) is from the index date onwards.
Attrition
How many people and records each step of a cohort definition removes. Cohort tables record it automatically.
cdm_reference
The cdm object in R. It holds one handle per table (cdm$person), and queries on them run inside the database.
summarised_result
The standard long table of aggregate results. summarise*() functions produce it; table*(), plot*() and OmopViewer read it.
Network study
One study run by several data partners on their own data, with only aggregate results shared.
Synthetic data
Generated patients for practice, loaded with omock. GiBleed is a small teaching dataset; synpuf-1k is about 1,000 synthetic US Medicare claims patients.
